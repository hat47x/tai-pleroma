# PoC完成後の評価プロトコル（案・2026-11-06）

Status: **提案**。生産性の結論ではない。完成後に測るための手順と観測点を先に固定しておく文書。

## 目的

「TEIによる構築へ移行したことで、生成AIを用いた開発の効率と自律性がどう変わったか」を、完成後の製品に対して測れる形にする。PoC中には評価しない（中間評価を人の判断材料にしない）という既定は変えない。

## 比較の単位

1変更（1つの意味の変更または不具合修正）を単位とする。同じ変更を次の2経路で実施し、差分を見る。

| 経路 | 内容 |
| --- | --- |
| B（基準） | 現行実装を直接編集する（TEIを介さない） |
| T（TEI） | 意味モデル（`.tei`）を変更し、契約・fixture・artifactを再生成して製品へ反映する |

比較条件を揃える: 同じ評価集合（テスト・確認項目）、同じ環境（OS・ツール版）、同じ完了条件（全テストPASS）。条件はreceiptへ記録する。

## 指標と観測方法

| 指標 | 定義 | 取得元 |
| --- | --- | --- |
| 変更から再生成までの時間 | 変更の決定から、全テストPASSのartifactが出るまで | `run_suite.py`の段ごとの`seconds`、`measure_workflow.py`の記録 |
| 手修正の量 | 生成物へ加えた差分の行数・箇所数 | `git diff`の統計（意味修正と生成器修正を分けて記録） |
| 人の介入回数 | 指示・確認・やり直しの回数と種類 | 作業ログ、PRのレビュー往復、再実行回数 |
| 試行回数 | 失敗して再試行した回数と原因分類 | `run_suite.py`の`attempts`、receiptの`result` |
| 文脈量 | 生成AIへ渡した意味・コードの量 | 入力ファイルの行数・バイト数（精度と併記） |
| レビュー指摘 | 生成物への指摘件数と種類（意味・実装・運用） | PRレビュー記録 |

## 手順

1. 評価集合を固定する（製品ごとのテスト段と確認項目。`run_suite.py`の段がそのまま使える）
2. 変更候補を10件程度選ぶ（意味の変更・不具合修正・追加を混ぜる）
3. 各変更をB→T、T→Bの順で実施し、順序効果を相殺する
4. 各実施で上表の指標をreceiptへ記録する（`schema: tai.reference.poc-evaluation/v0`を新設する）
5. 変更ごとの差分を集計し、中央値と範囲で示す。単一の「生産性倍率」は出さない

## 解釈の制約

- 結果はこのリポジトリの製品群と評価集合に限る。一般的な生産性の証明にしない
- 人の作業時間・長期保守性は測らない（PoCの範囲外）
- 自律性は「人の介入回数」と「介入の種類」で見る。介入ゼロを自律の証拠にしない
- 指標の悪化は隠さず併記する（文脈量の削減が精度を落とす場合など）

## 前提条件（未充足）

- 製品が完成していること（受入の配線、実インフラでの配備を含む）
- 評価集合が安定していること（段の追加・削除を評価期間中に行わない）
- 比較対象Bの実施者と環境が揃っていること
