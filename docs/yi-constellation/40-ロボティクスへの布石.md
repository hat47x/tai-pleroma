# ロボティクスへの布石

状態: 構想（2026-11-02）。製品の役割と最小の核の提案であり、実装、採用、安全認証の約束ではありません。

## 1. 前提

ロボティクスの時代には、ロボットがセンサーの時系列、動作のログ、安全の制約、人とのやり取り、現場の物理的な文脈を生む。ロボットは、リアルタイムで動き、事故の責任を伴い、人間の介入を必要とする。

系列は、ロボットを作らない。安全制御器にもならない。リアルタイムの制御プレーンにもならない。系列の役割は、ロボットと人と組織の間の、ソフトウェアの通路を作ることである。

この資料は、各製品のロボティクスにおける役割を置き、いま作る最小の核と、今から備える方向と、将来課題を分ける。最小の核は、ロボット固有の標準がなくても作れる記録の形式である。将来課題は、ロボットの標準、安全認証、リアルタイム性、責任配分に依存する。

## 2. 共通の最小核

七つの製品に共通する最小の核は、四つの記録である。ロボット固有の項目を増やす前に、この四つを製品に中立な形で作る。

**出来事の記録。**

```
event_id, robot_id, task_id, timestamp,
actor_type (robot / human / system), actor_id,
action, authority_ref, safety_envelope_ref,
outcome, evidence_ref, handoff_ref
```

**受け渡しの記録。**

```
handoff_id, from, to, task_id,
sent, not_sent, ack, next_action, safety_envelope_ref
```

**判断の記録。**

```
decision_id, action, rationale, options, criteria,
authority_ref, assumptions, safety_constraints,
evidence_ref, revisit_condition
```

**意味の対応。**

```
source_step, target_step, role, permission,
status (same / split / merged / dropped / new),
owner, loss_note
```

この四つは、ロボットの種類に依存しない。ROS 2でも、OPC UAでも、独自のAPIでも、同じ記録に写せる。製品は、この記録を持つことで、ロボットの標準が変わっても、通路を失わない。

## 3. 各製品の役割と最小の核

### 3.1 TAI

**ロボティクスでの役割。** ロボットの判断と、人の判断の受け渡し。ロボットが決めた作業を、人が受け取り、次の作業へ渡す。異常時の人への引き継ぎ。人の介入の記録。

**いま作る最小の核。** 受け渡しの記録に、ロボットID、作業ID、行為者（ロボット、人、システム）、権限の参照、安全エンベロープの参照、受け取りの返答を加える。ロボットと人の間の受け渡しを、一枚のカードにする。

**今から備える方向。** 出来事の記録の形式を、製品に中立なJSONで定義する。ロボットのAPIは、アダプターで対応付ける。リアルタイムの制御には入らない。人の介入と緊急停止の記録を、最初から持つ。

**将来課題。** 複数台のロボットの受け渡し。ROS 2のアクションとトピックの対応付け。安全認証された制御器との接続。リアルタイムの遅延保証。

### 3.2 SUI

**ロボティクスでの役割。** ロボット導入の現場の声を集める。作業者、住民、利用者の違和感、安全の観察、少数の懸念を、消さずに残す。ロボットの動作に対する現場の反応を、設計へ戻す。

**いま作る最小の核。** 声のカードに、導入の文脈（現場、作業、ロボットの種類）、安全の観察、少数意見の欄を加える。カードは、書いた人の言葉と出所を保つ。

**今から備える方向。** 現場の文脈を、タグではなく、短い構造化された項目で持つ。匿名性を保つ。声を、要約で消さない。

**将来課題。** 複数拠点の声の比較。ロボットの操作者からのリアルタイムの声。音声や映像の記録との接続。安全インシデントの通報との連携。

### 3.3 SHO

**ロボティクスでの役割。** 安全の手順書、作業標準、古いマニュアルから、ロボットの作業手順を作る。手順の文ごとに、原本の出所を付ける。原本にない手順を、作らない。

**いま作る最小の核。** 原本と参照範囲を選び、文ごとの出所が付いた手順の概要を作る。参照範囲の対応表で、原本のどの節を使い、どの節を使っていないかを示す。生成前の検査で、原本がない、または参照範囲が空のときに、生成を止める。

**今から備える方向。** 標準やマニュアルの取り込みを、版ごとに残す。手順の文と、ロボットの動作の対応を、後から足せるようにする。原本の版が変わったときに、手順のどこが古くなったかを示す。

**将来課題。** ロボットの作業手順の標準形式への対応付け。シミュレーションの証拠との接続。安全認証の文書との連携。

### 3.4 SEI

**ロボティクスでの役割。** ロボットの動作の理由を残す。なぜその動作をしたか、誰が承認したか、どんな前提と安全の制約があったか。事故の後の振り返り。監査への説明。

**いま作る最小の核。** 判断の記録に、動作、理由、選択肢、基準、権限の参照、前提、安全の制約、根拠、再検討の条件を加える。ロボットの動作を、人の判断と同じ形式で残す。

**今から備える方向。** 監査向けの出力を、最初から設計する。動作の記録と、人の承認の記録を、同じ時間軸で並べる。記録の改ざんを防ぐ。

**将来課題。** センサーの時系列との接続。リアルタイムの動作ログの取り込み。規制ごとの監査テンプレート。複数台のロボットの動作の比較。

### 3.5 TEI

**ロボティクスでの役割。** 古い工程、役割、権限、規格を、ロボットの工程へ移す。移行の前に、何が残り、何が失われるかを示す。役割と権限の対応を、失わずに移す。

**いま作る最小の核。** 意味の対応に、移行前の工程、移行後の工程、役割、権限、状態（同じ、分割、統合、廃止、新規）、担当、失われるもののメモを加える。失われるものの一覧と、位置の検査と、承認の印を作る。

**今から備える方向。** 工程のモデルを、製品に中立な形式で取り込む。役割と権限の対応を、最初から持つ。移行の前に、失われるものを承認する。

**将来課題。** ロボットのワークフロー標準への対応付け。デジタルツインとの接続。複数拠点の工程の比較。安全認証の移行文書との連携。

### 3.6 EKI

**ロボティクスでの役割。** ロボットの余力（計算、時間、空間、能力）を、必要な場所へ回す。余ったロボットの時間を、別のチームや別の拠点へ渡す。返りの経路を作る。偏りを検査する。

**いま作る最小の核。** 余りの交換の一覧に、提供（資源、量、制約、期間）、依頼（必要、量、期限）、組み合わせ、返りの経路、安全の制約を加える。受益者の言葉の欄と、偏りの検査を作る。

**今から備える方向。** 能力の提供を、資源の提供と分けて持つ。安全の制約を、交換の条件に含める。返りの経路を、信と学習へ広げる。

**将来課題。** 複数拠点のロボットの余力の共有。市場の仕組み。責任の配分。安全の制約の標準化。

### 3.7 ハーネス

**ロボティクスでの役割。** モデル、ハーネス、ロボットの境界。ロボットの状態を読み取り専用で読み、ロボットの正本への書き込みを拒否する。受け渡しを記録する。提供元のIDと版を記録する。セッションを終了しても、ロボットの状態を消さない。安全エンベロープと緊急停止の状態を、記録に含める。

**いま作る最小の核。** セッションの記録に、読み取り専用、書き込みの拒否、受け渡し、保留、提供元、交換、セッションの終了、安全エンベロープ、緊急停止の欄を加える。

**今から備える方向。** 境界の形式を、製品に中立なJSONで定義する。ロボットのAPIは、アダプターで対応付ける。エッジとクラウドの分割を、最初から想定する。安全エンベロープを、最初から一級の項目にする。

**将来課題。** エッジとクラウドのリアルタイムの境界。ロボットのベンダーAPIの対応付け。安全認証との接続。複数台のロボットのセッションの管理。

## 4. いまから備える方向

第一に、記録の形式を、製品に中立なJSONで定義する。ロボットの標準が変わっても、記録の形式を変えずに済む。

第二に、リアルタイムの安全制御の外に立つ。系列は、記録と受け渡しを作る。ロボットの停止は、安全制御器が行う。系列が止めるのではない。

第三に、人の介入と緊急停止を、最初から記録に含める。ロボットの動作の記録には、誰が止めたか、いつ止めたか、なぜ止めたかを含める。

第四に、監査と責任の配分を、最初から設計する。ロボットの動作の記録は、誰が承認し、誰が責任を持つかを示せなければならない。

第五に、アダプターで対応付ける。ROS 2、OPC UA、MQTT、独自APIを、製品の記録へ対応付ける。製品は、特定のロボットのAPIに依存しない。

第六に、エッジとクラウドの分割を、最初から想定する。すべてをクラウドへ送らない。現場で閉じる記録と、クラウドで集約する記録を分ける。

第七に、シミュレーションの証拠を、記録に含める。ロボットの動作の前に、シミュレーションで確かめたことを、証拠として残す。

第八に、安全エンベロープを、一級の項目にする。ロボットの動作の記録、受け渡しの記録、判断の記録のすべてに、安全エンベロープの参照を持たせる。

## 5. 将来課題

- 安全認証。ISO 10218、ISO/TS 15066などの安全規格との接続。系列は、認証を取るのではなく、認証された制御器の記録を扱う。
- リアルタイム性。系列は、リアルタイムの制御に入らない。遅延の許容範囲を、記録の種類ごとに決める。
- 責任の配分。ロボットの動作の責任を、誰が持つか。系列は、記録を示すが、責任を決めない。
- ロボットのベンダーAPI。ROS 2、OPC UA、独自APIの対応付け。標準が変わったときの追従。
- 複数台のロボットの調整。受け渡し、余力の共有、動作の比較。
- 物理世界のデータ。センサーの時系列、映像、音声、位置。記録の量と、保存の期間。
- 規制。国や地域ごとの安全規制、監査の要件。
- デジタルツイン。シミュレーションと実機の記録の接続。

## 7. 洞察

第一に、最小の核は、ロボットではなく、記録である。ロボットの標準が変わっても、記録の形式が変わらなければ、系列は通路を失わない。

第二に、系列の価値は、制御ではなく、通路である。ロボットを止めるのは安全制御器であり、系列ではない。系列は、止めたこと、渡したこと、決めたことを記録する。

第三に、安全エンベロープは、ロボティクス時代の新しい正本である。系列は、安全エンベロープを記録するが、所有しない。所有するのは、安全の責任を持つ組織である。

第四に、人の介入は、ロボティクス時代の新しい受け渡しである。TAIとSEIは、人の介入を、最初から記録に含める。

第五に、いまから備えるべきは、スキーマである。ロボットの標準を待つのではなく、製品に中立な記録の形式を、いま作る。標準が来たら、アダプターで対応付ける。

## 8. 境界

- 本資料は、製品の役割と最小の核の提案です。実装、採用、安全認証の約束ではありません。
- 系列は、安全制御器でも、リアルタイムの制御プレーンでもありません。記録と受け渡しの層です。
- 安全エンベロープ、緊急停止、責任の配分は、安全の責任を持つ組織と、認証された制御器の領域です。
- ロボットの標準、規制、ベンダーAPIは、変わり得ます。本資料は、特定の標準に依存しません。
- 定量化、指標、検証は、本資料の対象外です。
