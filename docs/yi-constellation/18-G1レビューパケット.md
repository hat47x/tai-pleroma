# G1レビューパケット

状態: レビュー用の提案（2026-11-01）。採否を決めるのはOwnerであり、本資料は決定ではありません。

本資料は、[01](01-64卦のシステム地図.md)から[21](21-SHOの扱い.md)までの分析を、G1の判断に必要な形に縮めたものです。全部を読み直さなくても、ここで採否と次の作業を決められるようにしています。製品と卦の対応の強さは[20-製品と卦の対応レビュー](20-製品と卦の対応レビュー.md)、SHOの扱いは[21-SHOの扱い](21-SHOの扱い.md)にまとめました。

## 1. G1で決めること

1. 要求として残る15件の候補を、採用、条件付き採用、保留、見送りに分ける。
2. 既存の要求、受入検査、測り方へ移した10件を、その扱いで確認する。
3. 坎を、狭い探索候補として残すか、相の拡充に回すか、止めるかを決める。
4. ハーネスの境界（RQ-YI-023）を、系列全体の要求とするか、各製品の要求に分けるか、要求にしないかを決める。
5. 概要資料への反映の範囲と時期を決める。分析の受理前にデッキを変えないことを確認する。
6. 系列全体の要求の受理者を決める。TAIのOwnerか、製品群のOwnerか。

## 4. 横断の判断

### D1 ハーネスの境界を、どこに置くか

- 案A 系列全体の要求にする。TAIが境界を整理し、各製品が接続口を提供する。
- 案B 各製品の要求に分ける。SHO、SEI、TEIが、それぞれの接続口の要求を持つ。
- 案C 要求にせず、接続の設計原則に留める。

推奨は案Aと案Bの組み合わせです。系列全体の原則をTAIが持ち、具体的な接続口は各製品が持つ。案Cだけでは、ハーネスが製品の正本を書き換える事故を、要求として防げません。境界の検査の設計は、[13-設計ノート](13-設計ノート.md)の7節にあります。

### D2 TAIを「統合製品」と呼ぶか

- 案A 「輔相製品」と言い直す。泰の象伝と非目標に合わせる。
- 案B 「統合製品」を保ち、注記で「頂点ではない」と補う。
- 案C 呼び方を決めず、課題の横断という説明だけを保つ。

推奨は案Aです。ただし、TAIのREADMEと概要資料の両方に及ぶため、用語の変更は一度に決めます。

### D3 SHOの状態を、どう示すか

- 案A 概要資料とMMIのREADMEに、ADR-0024が提案中であり、SHOとしての製品定義が未確認であると一行で示す。`sho-composer`にはLICENSEと初期コミットしかないことも添える。三つの扱いの比較は[21-SHOの扱い](21-SHOの扱い.md)に置いた。
- 案B 現状のまま、注記だけで扱う。

推奨は案Aです。提示の強さと記録の状態のずれを、読者が誤解しないようにします。

### D4 坎を、どう扱うか

- 案A 狭い探索候補として残す。危険の最小単位を、既存の記録から棚卸しする。
- 案B 既存製品の相の拡充に回す。EKIのsecurity event、SEIの権限、TEIの監査を広げる。
- 案C 今は扱わない。

推奨は案Aです。ただし、中央監視やSIEMの置き換えを非目標にし、危険の最小単位の確認だけで止めます。

### D5 系列全体の要求を、誰が受理するか

- 案A TAIのOwnerが受理する。
- 案B 製品群のOwnerが受理する。
- 案C 各製品のOwnerが、自分の製品に関わる部分だけを受理し、系列全体の要求は作らない。

推奨は案Cを基本にし、系列全体の要求（001、018、019、023）だけを案Aで扱うことです。系列全体の要求を増やすと、正本の所在が曖昧になります。

## 5. 証拠の要約

確かめたこと。

- SCN-001の参照評価は、基準で `passed=true`、終了コード0。
- 変種AからEで、仮承認のリンク切れ、リンク先の取り違え、廃止済み判断の復活、現行判断と廃止済み判断の対象の取り違えを、検査の失敗として観測した。
- 六つ目の変種Fは、最初は対象外のDecisionのリンク切れを検査せず、`passed=true` で通った。全てのDecisionのdraftとsubjectの解決を検査するN-09を追加し、変種Fが失敗することを確認した。
- 七つ目の変種Gでは、版のずれをN-10で検出する。N-09はリンクの解決、N-10は版の一致だけを検査する。
- 八つ目の変種Hでは、対象外のDecisionの公開承認をP-04が検出する。権限の主張は、リンクより先に一般化されていた。権限の実質と意味の妥当性は、まだ検査していない。
- 九つ目の変種Iでは、枯渇した根拠だけを持つDecisionが、保留として構造を通る。枯渇して止まっていることの検知は、まだ検査していない。
- 64卦表、8×8配置、36変爻、綜卦、序卦は、[19-構造の検算](19-構造の検算.md)で0件のエラーだった。36の象の引用と、序卦伝・雑卦伝の八つの引用も一致した。意味の解釈は検算の対象外である。
- ハーネス境界の参照実装は、読み取り専用、書き込み拒否、文脈の受け渡し、セッション終了後の正本の読み取りの四つが`passed=true`。実製品には接続していない。
- 製品と卦の対応は、20で製品の定義と要求から点検した。TAI、SEI、TEIは強い対応、SUI、EKIは中程度、SHOは弱い対応である。
- MMI読み取り専用の参照接続は、`go test`で `ok`。SCN-001の参照評価も `ok`。
- SEIの判断記録の参照接続は、`go test ./... -count=1`で22.5秒の `ok`。初回は入出力の解析で失敗したが、JSONを読む呼び出しを標準出力だけに変え、変更後の2回の試験で通った。
- 変種は`transition_test.go`に固定し、`go test ./... -count=1`で再現できる。

確かめていないこと。

- 実SUI、SEI、TEI、SHO、EKIの動作。
- SHOとSEIの中心の受け渡し。接続も要求もない。
- ハーネスと製品の正本の境界。
- 利用者にとっての有用性、意味の受理、公開の承認。

## 6. 見送る条件

次のいずれかが成り立つなら、その候補は見送ります。

- 既存の要求で足りることが、受入シナリオの全文照合で分かる。
- 検査を設計しても、前後の違いが観測できない。
- 新しい中央基盤や、製品間の権限拡大を要する。
- 卦の読みが、名前の事後正当化になっている。
- 製品の性格を変える拡張になる。

## 7. G1の後

1. 採用した候補を、各製品の要求文書へ移す。要求IDは各製品の体系へ採番し直す。
2. 条件付き採用の候補は、先に検査を設計し、結果を見てから要求へ移す。
3. 保留の候補は、棚卸しの後に再検討する。
4. 概要資料の更新は、分析の受理後に、独立した変更として行う。
5. G2、G3、G4、G5の順で進める。各ゲートの材料は[07-計画](07-計画.md)にある。
