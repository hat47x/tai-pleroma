# 受信者を表す欄をどこへ置くか（2026-11-18）

状態: 設計の比較と推奨。**SUIの契約を変更する提案ではなく、SUIのOwnerへ渡す材料である。** TAIは製品のSource・Contract・Authorityを確定しない。

## 1. なぜこの問いが立つか

Pの計器を作るには、まず**受信者を表す欄**が要る。3ラウンドの実測で、SUIにはその欄が無いことが分かった。

| 実測 | 結果 |
| --- | --- |
| `AccessRequest`の欄 | `action`・`auth`・`resource`・`tenant`・`safe_mode`・`read_only`・`subject`。[`audience`/`recipient`は無い](../../../evaluations/records/YIC-audience-instrument-2026-11-18.json) |
| 依頼者のrolesを変える | 判定は変わらない |
| `share`の判定を変えるもの | `visibility`と`safe_mode`/`read_only`。[受信者では変わらない](../../../evaluations/records/YIC-share-guard-2026-11-18.json) |

**`subject`は「誰が求めているか」であり、`visibility`は「どこまで公開してよいか」である。** どちらも「誰に渡してよいか」ではない。

## 2. 3案の比較

Step 3.7の`architect`ロールによる比較を、そのまま記録する。

| 観点 | 案A: `AccessRequest`に追加 | 案B: `AccessResource`に追加 | 案C: `subject`を拡張 |
| --- | --- | --- | --- |
| 既存呼出し元の互換性 | **高**（省略可能な欄の追加） | 中（資源側のスキーマ変更） | **低**（`subject`の意味を変える） |
| 同じ資源を複数の受信者へ | 中（リスト化または複数要求） | **高**（資源ごとに独立） | 低 |
| `visibility`との重複 | **低**（公開範囲と受信者は別） | 中（資源の責務と重なる） | **高**（混在する） |
| 既存テストの意味 | **保たれる**（省略時は従来どおり） | 解釈の変更が要る | **変わる** |
| 受信者ごとの監査記録 | **取りやすい**（要求に残る） | 資源側の履歴に残る | 区別しにくい |

## 3. 推奨: 案A

理由:

- 既存の要求型に**省略可能な欄**を足すだけで、新しい正本を作らない
- `visibility`（公開範囲のポリシー）と`audience`（実際の受信者）を**別の欄**に分けられる
- 省略時は従来の挙動が変わらないため、既存の呼出し元とテストの意味が保たれる

**案Aは「受信者を判定する」ことまでは意味しない。** 欄を足すことは、判定を書くこととは別である。欄ができた後に、`audience`を変えて判定が変わる試験が必要になる。

**加えて、欄を足すだけでは足りない。** 外部PDPへ送るbodyを実際に組み立てて数えたところ、トップレベルは`action`・`readOnly`・`resource`・`safeMode`・`subject`・`tenant`で、`audience`は無い（[receipt](../../../evaluations/records/YIC-pdp-payload-2026-11-18.json)）。bodyは**明示的な欄の列挙**から作られており、`AccessRequest`に欄を足しても直列化を通さなければPDPへ届かない。

| 足す必要がある箇所 | 何をするか |
| --- | --- |
| `AccessRequest` | 欄を定義する |
| `_serialize_external_policy_request` | bodyへ載せる |
| PDP側の契約 | 受け取って判定に使う |

**「省略可能な欄を足すだけ」という見積もりは、この2箇所を見落としていた。** 変更の大きさを取り違えないよう、ここに記す。

## 4. 壊れる可能性

- 既存のスキーマ検証が未知の欄を厳しく拒否する実装なら、`audience`が受理されない
- `audience`を必須にすると、既存の呼出し元が壊れる

## 5. 最小の試験（SUIのOwnerが実施する場合）

1. **後方互換**: `audience`を省略した要求が、従来と同じ判定を返す
2. **新機能**: `audience`を指定した要求で、その受信者にだけ許可される（同じ資源・異なる受信者で判定が変わる）
3. **fail-closed**: `audience`を空にすると拒否される

## 6. 判断を保留する点

- `audience`が単一値かリストか。同じ資源を複数の受信者へ同時に渡す用途の有無で決まる
- `AccessResource`側で公開範囲と受信者の両方を持つべきか。現行の判定は要求側にあるため、要求側が主軸と見た
- 受信者の識別子をどの粒度にするか（利用者・組織・Harness のどれか）

## 6.5 独立レビューが指摘した飛躍

Step 5 Previewの`independent-reviewer`ロールに、この3ラウンドの主張をレビューさせた。指摘は3つとも妥当だった。

### 6.5.1 「無い」は不在証明ではない

| 主張 | 飛躍 |
| --- | --- |
| `AccessRequest`に欄が無い → Pの判定はできない | **第1**: 欄が無いことは、受信者情報が決定経路に存在しないことを意味しない（PDPのコンテキスト属性・対象の所有関係・下流のenforcement側がありうる）<br>**第2**: 「読んだファイルに見つからなかった」は「定義されていない」ではない |
| `share`の判定はvisibilityとモードで決まる | **1つの評価関数の Trace から全決定経路の全称判断を出している**。policy版・別エンジン・override・キャッシュ・visibility自体が対象限定リストを符号化している可能性が残る |
| 受信者の欄を足すのは3箇所 | **観測ではなく設計案の見積もり**。代替設計では箇所数が変わる |

### 6.5.2 探索範囲を広げて応えた

指摘の第2点（不在証明には探索範囲の記録が要る）に応え、SUIのAPIパッケージ**99ファイル**を6語で走査した（[receipt](../../../evaluations/records/YIC-recipient-search-2026-11-18.json)）。

| 分類 | 件数 | 意味 |
| --- | --- | --- |
| token-audience | 81 | JWTが誰宛か（文書の受信者ではない） |
| model-allowlist | 89 | テナントが使えるモデルの制限（文書の受信者ではない） |
| cli-argument | 7 | 引数名に語が含まれるだけ |
| network-allowlist | 4 | ホスト/CIDRの許可リスト |
| **未分類** | **16** | 人が読む必要がある |

**これは「見つからなかった」であって「存在しない」の証明ではない。** 未分類16件を残したまま、「無い」とは書かない。

### 6.5.3 一般化を取り下げる

指摘の第1点（SUIの1経路から製品群全体を結論づけている）に従い、**「Pは測れない」という製品群全体の主張を取り下げる**。

本資料が言えるのは:

> **SUIの`AccessRequest`経路では、受信者を表す欄が確認できなかった。**
> **TEI・SHO・EKIの経路は未走査である。**

### 6.5.4 独立レビューが挙げた、次に確かめるべきこと

1. `AccessRequest`の生成箇所・別バリアント・シリアライズ・テスト・fixtureを列挙する（不在証明の補強）
2. 決定経路のどこかに受信者情報が供給されていないか
3. 共有系判断経路（policy版・エンジン・override・キャッシュ）を列挙する
4. Pの操作的定義（何が観測できればPの証拠になるか）
5. TEI・SHO・EKIに受信者を意識したゲートがあるか
6. **作用層（監査ログ・実際に誰に何が開示されたかの記録）から測れるか** — 意思決定経路ではなく結果観測という別経路

**6番目は、この3ラウンドで検討していなかった経路である。** 決定経路が測れなくても、結果の記録から測れる可能性がある。

## 6.6 作用層を実測した：記録できるが、記録する義務は無い

独立レビューが挙げた6番目の経路（作用層＝監査ログ）を、実際に測った（[receipt](../../../evaluations/records/YIC-audit-recipient-2026-11-18.json)）。

`AuditEvent`の封筒は10の欄を持つ:

```
actorRefHash, docId, eventId, eventType, metadata, occurredAt,
principalKind, safeMode, schemaVersion, tenantId
```

**受信者を表す欄は無い。** しかし`metadata`は自由な鍵を受け、`audience`・`recipient`・`sharedWith`は**sanitizeを通っても残る**（sanitizeが伏せるのは秘匿系の鍵だけ）。

| 層 | 受信者を記録できるか |
| --- | --- |
| 決定（`AccessRequest`） | **欄が無い** |
| 作用（`AuditEvent`の封筒） | **欄が無い** |
| 作用（`AuditEvent.metadata`） | **書ける。ただし任意** |

### 6.6.1 観測から測る道は、決定経路より現実的

決定経路には欄が無いので、そこからは測れない。しかし作用層には**置き場所がある**。記録があれば、そこからPを測れる。

**ただし3点を先に決める必要がある。**

1. **誰が記録するか** — `metadata`は呼出し側が渡す。サーバが自動で入れる仕組みは無い
2. **記録が無いことを「開示していない」と読めるか** — 読めない。記録の欠落は「記録しなかった」であって「開示しなかった」ではない
3. **`metadata`は自己申告である** — サーバが観測した事実ではない。既存の`context-audit`も同じ性質を持ち、`serverVerified=false`を付けている（[THREAT_MODEL](../../../../sui-sensemaking/THREAT_MODEL.md)相当の記述）

**この3点は、この3ラウンドで確かめた「リテラルの`true`は測っていない」と同じ構造である。** 記録があることと、その記録が正しいことは別である。

## 6.7 EKIには受信者の判定がある（対象はLease）

独立レビューは「SUIだけを見て一般化するな」と指摘した。その指摘どおり、EKIには**受信者を判定に入れている**箇所がある（[receipt](../../../evaluations/records/YIC-eki-recipient-2026-11-18.json)）。

`leasedelivery`の`Verify`は、Leaseの`WorkerIdentity`がローカルWorkerと一致するかを比較し、一致しなければ`ReasonSubjectMismatch`で拒否する。

```go
if lease.WorkerIdentity() != v.cfg.WorkerIdentity {
    return Verified{}, failure(decisiontrust.ReasonSubjectMismatch, "Lease recipient differs from the local Worker")
}
```

送出側も、呼出し側が受信者を指定できない:

```go
// The caller cannot supply a recipient or bytes to Service.Send.
```

| 製品 | 受信者を判定に入れているか | 対象 |
| --- | --- | --- |
| SUI（`AccessRequest`） | **入れていない** | 文書の開示 |
| EKI（`leasedelivery.Verify`） | **入れている** | Leaseの受信者がWorkerか |
| TEI（`-disclose`） | **入れていない** | Sectionの選択 |

**EKIの受信者判定は、「誰に文書を見せてよいか」とは対象が違う。** Leaseを渡してよいWorkerか、という判定である。したがって「EKIには受信者判定があるからPは測れる」とは言えない。

**しかし「SUIに無いから製品群に無い」も言えない。** 独立レビューの指摘は正しかった。製品ごとに、判定の有無と対象が違う。

### 6.7.1 この読み取りの限界

**ソースの読み取りであって、実行ではない。** 署名付きLeaseのfixtureを組み立てていないため、この比較が実際に走ることは確かめていない。前ラウンドまでの「リテラルを実行と読まない」と同じ規律を、ここにも適用する。
