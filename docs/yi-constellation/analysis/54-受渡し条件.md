# P・T・C・Hの受渡し条件（2026-11-18）

状態: 設計の整理。提案であり、Owner受理・実装・実機検証ではない。G1は未了のまま扱う。

本資料は、Step 3.7の`architect`ロールが出した次の一歩——**「G1判断を受領した直後にP・T・C・Hを動かせるよう、受渡し条件と最小検証セットを先に定義する」**——に応えるものである。到達点の現状は[I/R/P/T/C/Hの到達点](../irptch-reach-2026-11-16.md)にある。

## 1. 前提: 現行の計器では測れない

§4.8で確認したとおり、SHOのclaims moduleは**29個のclaimのうち2個しか計算していない**。I・T・Cの`true`はリテラルであり、R・P・Hの`false`／`'not-run'`もリテラルである。

したがって以下を分けて考える。

| 種類 | 意味 |
| --- | --- |
| **計器がある** | 与えた入力から値が変わる |
| **計器がない** | 何を与えても値が変わらない |

**受渡し条件は、計器がない段階について「何を測れば成立と言えるか」を先に決めておくもの**である。今すぐ測れるという意味ではない。

## 2. 段階ごとの受渡し条件

### 2.1 P（受信者別の開示）

| 項目 | 条件 |
| --- | --- |
| 判定主体 | 開示するProduct（Sourceを保持する側） |
| 入力 | Subject、Audience（受信者の識別子）、用途、Sourceの版 |
| 成立と言える観測 | `audience`を変えると判定結果が変わること（同じSubjectで2通り以上） |
| 反例 | `audience`を変えても結果が変わらない（＝判定していない） |
| 現在の状態 | **計器なし**。`knowledge-context -disclose`はSectionの選択であり、Audienceで変わらない（[§4.1](../irptch-reach-2026-11-16.md)）。SUIの`AccessRequest`にも`audience`／`recipient`の欄が無く、依頼者のroles/groupsを変えても判定が変わらなかった（[実測](../../../evaluations/records/YIC-audience-instrument-2026-11-18.json)） |

**最小検証セット**（計器を作る場合に最低限必要な試験）:

1. 同じSubject、異なるAudience 2件で、片方だけ許可される
2. Audienceを空にすると拒否される（fail-closed）
3. 許可されたAudienceでも、Sourceが改訂されると再確認を要求する

**まず何が要るか**：受信者を表す欄。SUIの`AccessRequest`は`action`・`auth`・`resource`・`tenant`・`safe_mode`・`read_only`・`subject`を持ち、**`subject`は「誰が求めているか」であって「誰に見せてよいか」ではない**。欄が無い状態では、受信者を判定する試験を書いても入力が渡せない。

**`share`というactionを実測した結果**（[receipt](../../../evaluations/records/YIC-share-guard-2026-11-18.json)）: SUIには`share`がある。何が判定を変えるかを一つずつ動かして確かめた。

| 変えたもの | 判定は変わったか |
| --- | --- |
| 依頼者のroles（`reader` → `admin`） | **変わらない**（どちらも`policy_ref_missing`） |
| resourceのvisibility（`Org` → `Public`） | **変わる**（`Org`は`policy_ref`必須、`Public`は不要） |
| `safe_mode` | **変わる**（`safe_mode`で拒否） |
| `read_only` | **変わる**（`read_only`で拒否） |
| 受信者 | **動かせない**（欄が無い） |

**visibilityは「どこまで公開してよいか」であって「誰に見せてよいか」ではない。** この2つを同じ欄で扱うと、公開範囲の広い文書を狭い相手に見せる判断ができない。Pの計器には、公開範囲とは別の受信者の欄が要る。**その欄をどこへ置くかは[受信者の欄](55-受信者の欄.md)に3案比較として整理した**（推奨は`AccessRequest`への追加。SUI Ownerへの材料であり、TAIは変更しない）。

### 2.2 T（配送）

| 項目 | 条件 |
| --- | --- |
| 判定主体 | 送り出すProduct（Producer） |
| 入力 | 投影済みpayload、受信先の識別子、現在のGrant |
| 成立と言える観測 | **別Process**がpayloadのbyteを受領し、digestが一致すること |
| 反例 | 同一Process内の関数呼出しを「配送」と呼ぶ |
| 現在の状態 | **限定的な計器あり**。SHOのrunnerで`newProcessRereceive: true`を観測（ただしclaimはリテラル、§4.8） |

**最小検証セット**:

1. Producer と Consumer が別Processであること（PIDまたはSessionで示す）
2. 送出byte数とdigestの一致
3. 部分受領を成功にしない（切断を注入）
4. 受信先が異なれば拒否される

### 2.3 C（実Consumer受領）

| 項目 | 条件 |
| --- | --- |
| 判定主体 | 受け取るProduct（Consumer） |
| 入力 | payload、独立Expected |
| 成立と言える観測 | Consumerが**実Bodyを読み**、独立Expectedと比較した結果を返すこと |
| 反例 | digestの一致だけを「読んだ」と呼ぶ |
| 現在の状態 | **限定的な計器あり**。`actualConsumerRead: true`はトップレベルで観測される |

**最小検証セット**:

1. Consumerがpayloadの本文を読んだこと（byte範囲または全文digest）
2. 独立Expected との比較結果（一致・不一致の両方）
3. 意味の受理（`meaningAccepted`）とは別欄であること

### 2.4 H（Harness Reply）

| 項目 | 条件 |
| --- | --- |
| 判定主体 | 外部Harness |
| 入力 | Tool Call、Toolの版、Session |
| 成立と言える観測 | Replyの**終端**と本文が受領され、Sessionが同定できること |
| 反例 | Tool呼出しの開始だけを「Reply」と呼ぶ |
| 現在の状態 | **成立条件を測る計器は無い**。ただし`harness-adapter`には4種のadapterの記録がある（[Hの計器](56-Hの計器.md)）。`otherHarnessLiveExecution: 'not-run'`は**Hの成立（Reply終端・Session同定）を測っていない**という意味である |

**最小検証セット**:

1. 実Harnessへの実Tool Callと、そのReply終端
2. Sessionの同定（再接続可否を別に記録）
3. 部分Replyを完全Replyと呼ばない

## 3. G1の判断が変わらせるもの／変えさせないもの

| 項目 | G1の判断で変わるか |
| --- | --- |
| Pの判定主体をどのProductに置くか | **変わる**（候補の採否がSubjectの範囲を決める） |
| T・Cの最小検証セット | **変わらない**（製品をまたぐ機構の性質） |
| Hの計器の要否 | **変わらない**（外部Harnessの性質） |
| 各段階の「成立」の定義 | **変わらない** |

**つまり、G1を待たずに決められる部分がある。** 本資料はその部分を先に固定する。
