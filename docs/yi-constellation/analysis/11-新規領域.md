# 新規領域

状態: 提案（2026-11-01）。新しい製品の追加や、既存製品の拡張を決めるものではありません。

本資料は、64卦の地図と変爻の分析から、新規領域を二つの方向と一つの区分で検討します。一つは、卦まるごとの欠落に気づき、新しい製品を追加する方向。もう一つは、既存の製品が担う相を拡充する方向。そして、製品にも相の拡充にもせず、媒体として空けておく区分です。本分析の結論は、相の拡充を優先し、新規製品は一つに絞って探索し、媒体は製品の候補から外す、というものです。

## 1. 二つの方向

### 1.1 方向A 卦まるごとの欠落から新しい製品へ

64卦のうち、製品のない卦が58あります。しかし、58の卦が58の製品を意味しないことは、製品群の概要資料も明記しています。新しい製品を検討できるのは、次の条件を満たす卦だけです。

- その卦が表す能力を、既存のどの製品も担っていない。
- その能力が、製品として独立した正本とライフサイクルを持つ。
- 利用者と、価値の測り方が具体的にある。
- 中央のHostを要しない。
- 既存製品の未確認領域が、その能力の不在を示している。

### 1.2 方向B 各製品が担う相の拡充

変爻の分析は、各製品の六つの局面のうち、どれが強く、どれが薄いかを示しました。薄い相は、製品の欠陥ではなく、選んだ重点の裏側です。相の拡充は、新しい製品を足さずに、既存の製品が扱う局面を広げます。

本分析は、方向Bを既定とします。方向Aは、方向Bでは埋まらない能力が、利用者の具体的な仕事として残る場合に限ります。

## 2. 方向Aの判定

### 2.1 判定基準

| 基準 | 問い |
| --- | --- |
| C1 非目標の確認 | 既存製品の非目標が、その能力を明確に拒んでいるか。拒んでいないなら、既存製品の拡張で足りる可能性が高い |
| C2 正本とライフサイクル | その能力に、独立した正本、版、廃止の単位があるか |
| C3 利用者と測定 | 誰が使い、何で価値を測るかが具体的にあるか |

| C5 不在の証拠 | 既存製品の未確認領域が、その能力の不在を示しているか |

### 2.3 坎を残す理由

坎は、六つの製品のどれも中心に置いていない危険の相です。既存製品の非目標は、危険の検知を明確に拒んでいません。EKIの脅威モデルは設計時の前提であり、SEIの権限は意味の参照の範囲であり、TEIの監査は業務の説明です。どれも、危険が現に起きたときの検知、停止、事後の証跡を、製品の中心にしていません。

既存製品の未確認領域も、坎の不在を示します。TAIの公開gateは保留であり、EKIの本番委任は未確認であり、TEIの実環境の外部接続は未確認であり、SEIの実運用の権限は未確認です。危険の相は、各製品の未確認の底に共通してあります。

ただし、坎を製品にするなら、範囲を狭く定める必要があります。次を非目標にします。

- 他製品の内部を常時監視する中央の監視基盤にしない。
- 組織のSIEMやSOCを置き換えない。
- 危険の予知を約束しない。
- 検知のために、製品間の権限を広げない。

最初に確かめるのは、危険の最小単位です。権限の逸脱、委任の拒否、権限の期限切れ、検証の失敗、公開の拒否。どれが、既存の記録から観測でき、どれが観測できないか。坎の製品が要るかどうかは、この確認の後に決めます。

**2026-11-11に確かめた**: 既存のreceipt 300件を検索し、5つの単位のそれぞれが何件のreceiptに現れるかを[数えました](../../../evaluations/records/YI-danger-units-2026-11-11.json)。

| 単位 | 現れるreceipt |
| --- | --- |
| 権限の逸脱 | 13件 |
| 委任の拒否 | 37件 |
| 権限の期限切れ | 15件 |
| 検証の失敗 | 32件 |
| 公開の拒否 | **2件**（宣言`publicationAllowed: false`は286件） |

**公開の拒否だけが観測として乏しい**ことが分かりました。286件のreceiptは「公開しない」と宣言しているだけで、公開が実際に拒否された場面は2件です。危険の最小単位は、4つは既存の記録で観測でき、公開の拒否だけは観測が足りません。

### 2.4 革を製品にしない理由

革は、鼎の綜卦であり、置き換えと廃止の手続きです。TEIの価値は技術を選び直せることを掲げ、実行先やデータベースの交換を扱います。革の能力は、TEIの相の拡充として置く方が、正本と責任の所在が明確になります。独立した製品にすると、TEIの知識のモデルと、移行の手続きが、二つの正本に分かれます。

ただし、製品をまたぐ移行（たとえば、ある製品の廃止に伴う課題の引き継ぎ）は、TAIの課題の横断として扱います。革の手続きは、TEIの要件（RQ-YI-012）と、TAIの移行の記録に分けます。

### 2.5 損、觀、節を製品にしない理由

損、觀、節は、いずれも既存製品の運用の中で扱える操作です。損はEKIの停止と取消、TAIの減らす運用。觀はTAIの通塞の観測、SEIの到達の記録。節はEKIの予算と期限、TEIの制約。独立した製品にすると、既存製品の記録を集めるだけの、中央の表示層になりがちです。これは、シリーズが避けてきた中央Hostの再導入になります。

否と困は、製品ではなく状態です。否はTAIの診断、困は全製品の枯渇の検知として扱います。中孚は、信頼という性質であり、製品の能力ではありません。

### 2.6 巽を製品にしない理由

巽は、製品の卦として空いていますが、製品にする卦ではありません。[15-生成AIハーネスの卦読み](15-生成AIハーネスの卦読み.md)は、巽を生成AIハーネスの卦として読みました。ハーネスは、利用者の意図、文脈、ツール、権限、観測を中継する媒体であり、製品ではありません。

巽を製品にすると、媒体が前に出ます。雑卦伝の「兌見而巽伏」は、巽が伏することを対比として示します。ハーネスは、見えない方がよい。見えるのは、画面と成果です。ハーネスを製品化すると、利用者は媒体と成果を取り違え、製品群の正本も空洞になります。

このことは、新規領域の判定に第三の区分を加えます。製品、相の拡充、媒体です。卦が空いていることは、製品の必要性の証拠になりません。危険の検知（坎）や上限の設定（節）も、製品にせず、ハーネスや組織の権限として持つ方がよい場合があります。

## 3. 方向Bの相の拡充

各製品の薄い相と、拡充の具体を整理します。ここでの拡充は、新しい画面やAPIの追加を意味しません。既存の要求と記録の範囲で、扱う局面を広げることを意味します。

| 製品 | 薄い相 | 拡充の具体 | 要件 |
| --- | --- | --- | --- |
| TAI | 三（反転の準備）、上（崩壊後の始末） | 否の診断を、失敗の分類として持つ。崩壊後に、蓄える、閉じる、始め直すを選ぶ | RQ-YI-001、002、022 |
| SUI | 五（権威で集める場の信頼）、上（集めきれない場合の解放） | 集めきれなかった場を、未解決を残して畳む。位で集める場の信を、別に確かめる | RQ-YI-004、020 |
| SHO | 三（空邑）、上（冥升） | 原本の裏づけがない移行を、事前に検出する。昇りの上限と、修復の経路を持つ | RQ-YI-005、006、022 |

SHOの製品としての扱いは[21-SHOの扱い](21-SHOの扱い.md)で整理中です。SHOをMMIの役割とする場合、空邑と冥升は、MMIの来歴層の検査として読み直します。
| SEI | 初（放置）、二（漏洩） | 参照されない記録と、狭い用途への漏れを、読み取り専用で検知する | RQ-YI-007、008、016 |
| TEI | 三（運搬）、四（過剰実行） | 契約と移行の手段を、完成の条件に含める。権限を超えた実行を、設計段階で拒否する | RQ-YI-010、011、012 |
| EKI | 三（凶事）、上（フリーライド） | 非常時の委任の型を持つ。提供と受益の対応を、計算の条件の範囲で記録する | RQ-YI-013、014、015 |

相の拡充は、製品の性格を変えません。TAIは輔相のまま、SUIは集めて決めないまま、SHOは原本を残したまま、SEIは汲める井戸のまま、TEIは器のまま、EKIは委任の核のまま、扱う局面を広げます。

## 4. 新規領域の探索課題

新規領域を決める前に、次の三つを確かめます。

### 4.1 危険の最小単位

- 問い: 権限の逸脱、委任の拒否、権限の期限切れ、検証の失敗、公開の拒否のうち、どれが既存の記録から観測でき、どれが観測できないか。
- 確かめ方: 各製品の負例と状態文書から、危険の事象を抽出し、観測の有無を分類する。
- 成果物: 観測できる危険の一覧と、観測できない危険の一覧。

### 4.2 相の拡充の優先順位

- 問い: 六つの製品の薄い相のうち、どれが最も利用者の仕事に近いか。
- 確かめ方: 各製品の利用場面と未確認領域を照らし、薄い相が実際の仕事の妨げになっている箇所を探す。
- 成果物: 拡充の優先順位と、その根拠。

### 4.3 新規製品の判定

- 問い: 坎の能力は、既存製品の相の拡充では埋まらないか。
- 確かめ方: 危険の最小単位のうち、EKI、SEI、TEI、TAIのどれも扱えないものを特定する。一つでも扱えるなら、その製品の拡充を先に検討する。
- 成果物: 新規製品が要るかどうかの判断と、要る場合の最小の範囲。

## 5. やらないこと

- 58の卦を、58の製品にしない。
- 卦が一つあるという理由だけで、製品を追加しない。
- 新規製品の検討を、既存製品の欠陥の指摘にしない。
- 相の拡充を、製品の性格の変更にしない。
- 中央の監視、統一データベース、共通の統合標準を作らない。

## 6. 判断を求める点

1. 坎を、狭い探索候補として残すか。残す場合、危険の最小単位の確認を、どの製品の記録から始めるか。
2. 革、損、觀、節を、相の拡充として扱うか。扱う場合、どの製品の要求へ戻すか。
3. 相の拡充の優先順位を、利用者の仕事と未確認領域のどちらを先に置いて決めるか。
4. 新規製品の判定を、誰が行うか。Owner判断が要る点として、どこに記録するか。
