# G1の判断が下りた後の手順

状態: 手順書（2026-11-11）。判断そのものではなく、判断が下りたときに何をどの順で行うかを書いたものである。

本資料は、[18-G1レビューパケット](18-G1レビューパケット.md)の判断欄が記入された後に、TAIと各製品が何を行うかを、実行できる形にしたものである。**今は何も実行しない。** 判断が来たときに、そのまま動けるようにするための準備である。

## 1. 判断の記入（Owner）

1. パケット§4のD1〜D6の「判断: （未記入）」を、選んだ案と理由で埋める。
2. §2の15件の「判断」欄と、§3の10件の確認を埋める。
3. §9の記録（判断者・日付・対象・決定の要約・次に進む条件）を埋める。

**記入の順序**は§10.1のとおり（D5 → D6 → D1 → 15件 → D2/D3/D4）。

### 1.1 記入後に確かめること

```text
python integrations/tools/yi_g1_status_check.py \
  --artifact evaluations/artifacts/scn-003-document.json \
  --out evaluations/records/YI-g1-status-2026-11-11.json
```

- 判断欄6つと記録欄が埋まっていれば、`g1IsDecided`が`true`になる
- 同時に、**受理済みと主張する文書が現れる**ので、`documentsClaimingAcceptance`を見る
- この検査は「記入の有無」と「文書の状態表示」の一致だけを見る。判断の内容は見ない

## 2. D5の判断後: 受理者の決定を反映する

D5で「TAIが受理する」（案A）を選んだ場合、TAIの受理の役割を明文化する文書を足す。**TAIは既にOwner・ Sponsorの語を持っている**（[測定](../../../evaluations/records/YI-acceptance-authority-2026-11-11.json)：366件）。

案C（各製品のOwner）を選んだ場合、**SEI・EKI・SUI・MMIには受理の役割を名指す語が無い**ので、先に各製品の文書へ役割を書く必要がある。これはTAIの仕事ではなく、各製品のOwnerの仕事である。

## 3. D6の判断後: SHOの扱いを反映する

| 選んだ案 | 行うこと |
| --- | --- |
| 案A 独立した製品 | `sho-composer`のREADMEと要求文書を確認し、RQ-YI-005/006をSHOの要求IDへ移す。**SHOは既に72ファイル・135コミットを持つ**（[測定](../../../evaluations/records/YI-sho-actual-2026-11-11.json)）ため、「定義が無い」ではなく「薄い」前提で移す |

## 4. D1の判断後: ハーネス境界を反映する

案A（系列全体）＋案B（各製品の接続口）を選んだ場合、TAIは系列全体の原則を文書に持ち、各製品は接続口の要求を持つ。**TAIが既に持っているのは参照実装**（`tools/reference-harness-boundary`）であり、実製品の接続口ではない。

```text
  --artifact evaluations/artifacts/scn-003-document.json \
  --out evaluations/records/YI-g2-landing-2026-11-11.json
```

空き番号: SEI **24**、TEI **38**、EKI **65**、SUI **13**、MMI（ADR）**32**。

### 5.2 移すときの規則

- 各製品の作業規則（短命ブランチ・PR・CI）に従う
- 要求IDは各製品の体系へ採番し直す。`RQ-YI-###`は対応表としてTAIに残す
- **採用しなかった候補の理由を、本資料群へ残す**（反証の記録になる）

### 5.3 移した後の確認

```text

```
