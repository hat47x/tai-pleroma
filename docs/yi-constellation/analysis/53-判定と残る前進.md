## 3. 何が外部入力に依存しているか

### 3.1 G1の判断（Owner）

25件の候補の採否と、6つの横断判断。**TAIは判断していない**（`AGENTS.md`の「AIの提案を業務上の承認として扱わない」に従う）。

### 3.2 各製品の受理（各製品のOwner）

- 15件を要求文書へ移す（G2）
- EKIの`enforce_access`（`decision.read_only`を扱うか）
- EKIのRAC-1の本番配線
- SEIの参照の記録（参照されていない記録を示すための欄）
- MMIの行の無い範囲の検出
- TEIのapplication側の型解決

**いずれも製品の正本であり、TAIは横欄を足せない。**

### 3.3 実インフラ

実製品の接続、実IdP、実DB、公開CA、複数ホスト。TAIは参照実装と合成の記録までしか持てない。

最後に、**`result: PASS`なのに`observed`に「揃っていない」と書いてあるreceipt**が無いかを[点検しました](../../../evaluations/records/YI-pass-consistency-2026-11-11.json)。1件（`YI-g1-evidence`）が、`everyDecisionHasAnObservation: false`を持ちながら`finding`を書いていませんでした。「PASSは測ったことの成功であって、穴が無いことではない」と読む人が取り違える形です。`finding`を足し、D3の観測（`sho-composer`の実測）も反映して再生成しました。現在は30件すべてが、穴を明示しています。

### 6.1.1 点検それ自体の対象漏れが見つかった

**点検が「合格」と報告するとき、その点検が何を見ていないかを読む必要がある。** 件数を書いていない点検は、対象外の存在を隠す。

### 6.1.2 点検の数を、手で保っていた

集約が走らせる点検の数は、checker側に**整数の定数**として書いてある。点検を1つ足すたびに手で直す必要があり、今回の変更では**4箇所**を編集した（うち2箇所は同じファイル）。

**一致しているが、それは今回手で直したからである。** 手で保つ定数は、いずれ食い違う。**一致を確かめる点検を置いた**ので、食い違ったときに気づける。

### 6.1.3 検査の40件が、大小文字の違いで一度も動いていない

##### 6.1.6b receiptの`command`は、再実行できる形ではない

receiptは`command`欄に実行したコマンドを記録している。読者はそれを写して再現できると期待する。**その前提を確かめた**（[実測](../../../evaluations/records/YIC-cited-path-2026-11-28.json)）。

```text
検査したパス: 98件
既に存在しないパス: 82件（16種類）
```

| 消えたパス | 引用しているreceipt |
| --- | --- |
| `D:\GIT\hat47x\sui-wt-tenant` | **38件** |
| `D:\GIT\hat47x\tei-wt-cur` | 11件 |
| `D:\GIT\hat47x\tei-wt-main3` | 3件 |
| `D:\GIT\hat47x\sui-wt-ro` | 3件 |

**作業用のworktreeは、作業が終わると消される。** したがってreceiptの`command`は、**書かれた時点では再実行できたが、今はできない**。

### 6.1.4 これは「receiptが嘘」ではない

receiptは**その時点の実行を記録したもの**であり、消えたworktreeは記録の誤りではない。しかし:

| 読み手の期待 | 実際 |
| --- | --- |
| `command`を写せば再現できる | **パスが無いのでできない** |
| パスは今も同じ内容を指す | **指していない**（消えている） |

**receiptの`scope`は「測ったこと・測っていないこと」を書いているが、「再実行できること」は書いていない。** この3つ目を書く欄が無い。

### 6.1.5 記録に足すべきこと

**「このcommandは当時のパスに対するものであり、現在は再実行できない」**と読めるようにする。方法は2つあり、どちらも記録の変更であってreceiptの改変ではない。

1. パスが消えたreceiptに、その旨を注記する（履歴は残す）
2. 今後は、checkoutの**commit**を記録し、パスは補助情報として扱う

**2番目が本質的である。** パスは消えるが、commitは消えない。**再現性の根拠をパスからcommitへ移す**のが正しい。

**ただし、その提案がどれだけの書き換えを要するかを測った**（[実測](../../../evaluations/records/YIC-commit-field-2026-11-28.json)）。

| 項目 | 件数 |
| --- | --- |
| 実実行receipt | 297 |
| commitらしき欄を持つ | **59** |
| 持たない | **238** |

**8割のreceiptにはcommit欄が無い。** 「パスからcommitへ移す」は、**既存の記録の大半を書き換える提案**である。小さな変更として扱わない。

### 6.1.14.1 `tei-text-selection` は「狭めれば当たる」が、当ててはいけない

この語尾 `selection` を持つreceiptは4件あります。

### 6.1.14.2 3つの原因を区別する

**「発火しない規則は全部直す」は誤りです。** 直すべきは名前が届いていないもの、記録すべきは対象が無いものです。

**どちらも「名前が届いていない」という同じ症状で、原因が違います。**

規則照合だけを大小文字無視に書き換えて、checkerを**2回**走らせた（[比較](../../../evaluations/records/YIC-dead-rule-impact-2026-11-18.json)）。

| 実行 | 結果 | 誤り |
| --- | --- | --- |
| そのまま | PASS | 0 |
| 規則を大小文字無視に | **FAIL** | **22** |

**つまり40件の規則には実際の判定が書かれており、receiptはその判定を受けずに合格していた。** 出た誤りの例:

- `TEI artifact receipt has no projection schema`（4件）
- `TEI auth receipt did not record 200/401`
- `TEI target receipt did not pass 4 cases`

**receiptの側を確かめると、規則が要求する欄は本当に無い。** 規則が古いのかreceiptが不足なのかは、この比較だけでは決まらない。**決まらないことを「receiptが悪い」と読まない。**

### 6.1.15 この実験で2回、自分の改変が結果を汚した

1. 最初は`relative`自体を小文字にした → `"SCN-002" in relative`のような**規則内部の大小文字依存**まで壊れ、誤りはこちらの改変の産物だった
2. 次に**入れ子の分岐**（`if "D-08" in relative:`）まで書き換えた → 期待値の選択が変わり、やはり産物が混ざった

3回目で、**トップレベルの規則選択（8字下げ）だけ**を書き換えた。22件が残った。

**実験が対象を壊していないかを、結果より先に確かめる必要がある。**

### 6.1.16 落ちた22件を1件ずつ読んだ：8種類は欄が無い、1種類は値が違う

22件の誤りが「規則が古い」のか「receiptが不足」なのかを、receiptを読んで確かめた（[内訳](../../../evaluations/records/YIC-dead-rule-fields-2026-11-18.json)）。

| 誤り | 件数 | 要求された欄 | 実状 |
| --- | --- | --- | --- |
| `TEI artifact receipt has no projection schema` | 8 | `projectionSchema` | **無い** |
| `TEI consumer receipt did not record six read-only tests` | 3 | `passed`＝6 | **欄は在るが値が 3/4/5** |
| `TEI target receipt did not pass 4 cases` | 2 | `passed`＝4 | **無い** |
| `TEI target receipt did not pass the oneshot profile` | 2 | `oneshotPassed` | **無い** |
| `TEI assembler receipt did not pass 6 tests` | 2 | `passed`＝6 | **無い** |
| `TEI assembler receipt did not bind the card record` | 2 | `cardRecordBound` | **無い** |
| `TEI auth receipt did not record 200/401` | 1 | `authorizedStatus` | **無い** |
| `TEI auth receipt did not enable authorization` | 1 | `authEnabled` | **無い** |
| `TEI artifact receipt points at a missing file` | 1 | `artifactPath` | **無い** |

**「欄が無い」と「値が違う」は別の食い違いである。** 8種類は欄そのものが無く、1種類（TEI consumer）は欄は在るが値が違う。**まとめて「receiptが不足」と書くと、後者の読みを誤る。**

**どちらを直すかは製品Ownerの判断であり、ここでは決めない。**

 前者は用意できる材料の話、後者は観測の話である。11-11には後者を断定したが、その後の実測で**観測は増えた**。

ただし増えたのは**Pの計器の材料と、計器の天井の測定**であって、**Pを測れるようになったわけではない**。この区別を保つ。

### 6.1.17 同じファイルに現在の数と過去の数が並んでいた

`docs/status.md` は「現在の状態」の入口である。そこに**実実行receiptの数が2つ**あった（[実測](../../../evaluations/records/YIC-count-claim-span-2026-11-28.json)）。

| 位置 | 数 | 意味 |
| --- | --- | --- |
| L134（現在の状態） | **306件** | 実測と一致 |
| L141（2026-11-06の追記） | **186件** | その時点の数 |

`doc_consistency_check` は**最初の一致だけ**を検証する。**186件はどの検査も見ていなかった。**

### 6.1.17.1 直したのは書かれた文ではなく、「現在」と読む測り方

最初はL141を「当時（2026-11-06時点）の実実行receiptは186件」と書き換えた。**それでも点検は食い違いと言い続けた。** 文の中に `実実行receiptは186件` が残るためである。

**誤っていたのは、点検が日付を無視して「現在の主張」と扱ったことである。** 行に日付・「当時」・「時点」があれば履歴として扱うよう直した。**結果、現在について述べる主張の食い違いは0件。**

**文を直しても、読み方が誤っていれば判定は変わらない。**
