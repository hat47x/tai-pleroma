# 既存要求との照合

状態: 照合記録（2026-11-01）。要求文書の見出しと主要な本文を読み、候補を分類しました。全文の精読と、受入シナリオ・ADRの網羅的な確認はしていません。

本資料は、[05-要件候補](05-要件候補.md)の22件を、各製品の既存の要求と照合します。目的は、候補を増やすことではなく、既にある要求と重複する候補を落とし、残る候補を絞ることです。第一巡の候補は、読みから出た提案であり、既存の要求を十分に確認していませんでした。本資料は、その点を修正します。ハーネスから追加された3件は、9節で予備的に扱います。

## 2. 分類の基準

| 分類 | 意味 |
| --- | --- |
| 既存 | 既存の要求が、同じ内容をすでに満たしている |
| 受入検査 | 要求は既存だが、その要求を確かめる検査が新しい |
| 拡張 | 既存の要求の範囲を広げる。要求の追加ではなく、要求の改訂になる |
| 新規 | 既存のどの要求にも当たらない |

「新規」は、製品の要求として新しいという意味です。系列全体の方法や文書規律は、製品の要求ではなく、別の扱いにします。

## 4. 重複が大きい候補

第一巡の候補のうち、次の八つは、既存の要求で足ります。要求として追加せず、検査か価値の測り方へ移します。

- RQ-YI-006 昇の来歴。MMIの「由来の保持」とADR-0028が、source locator、変換条件、fingerprint、確認状態を求めています。成果から原本へ到達できるかの検査を、既存の要求へ足すだけです。
- RQ-YI-007 汲めることの検査。SEIのREQ-0005とREQ-0014、受入シナリオ「時間が経過した後、別のAIが当時のbasisを読み直し、Inquiryを再開する」が、後日の読み直しを求めています。運用の証拠は部分的ですが、要求とシナリオはあります。
- RQ-YI-009 担い手の交換。SEIのREQ-0007がProviderの中立性を求め、F5とsynthetic Provider A/Bで交換を検査しています。要求の追加は不要です。
- RQ-YI-011 凝命。TEIのRQ-028が、更新の前に、残る修正、未解決、実行できなくなる操作、切戻せる範囲を示すことを求めています。漂流の検知は、RQ-028の検査として足せます。
- RQ-YI-013 改過としての益。EKIのRQ-019、RQ-021、RQ-044が、結果の検証を求めています。価値の測り方として扱い、要求にはしません。
- RQ-YI-014 反哺の記録。EKIのRQ-036と受入シナリオが、Contribution RecordにBeneficiaryを残すことを求めています。受益元は、すでに項目としてあります。一方的取得の検出は、測り方として残ります。
- RQ-YI-015 損の設計。EKIのRQ-005、RQ-006、RQ-009、RQ-035が、停止、取消、上限を求めています。減らすことの価値は、測り方として扱います。
- RQ-YI-003 輔相の境界。TAIの非目標が、すでに同じ内容を定めています。新しい要求ではなく、レビューの観点にします。

## 5. 残る候補

要求として残すのは、新規の五つと、拡張の七つです。ただし、拡張は要求の追加ではなく、既存の要求の改訂として扱います。

### 5.1 新規の五つ

- RQ-YI-001 通塞の観測。系列をまたぐ滞留の記録。TAIの`evaluations/`または`docs/`。
- RQ-YI-018 四系の主張規律。価値文書の主張に、系と水準を付ける。全製品の文書規律。
- RQ-YI-019 変爻の検査。局面の変化を観測する方法。全製品の評価の手順。
- RQ-YI-020 中心の受け渡し。SHOとSEIの中心の接続。両製品の要求。
- RQ-YI-022 極まりの始末。成功の後の扱い。全製品の状態文書と要求。

### 5.2 拡張の七つ

- RQ-YI-002 否の診断。SEIの状態区別を、製品間の流れへ広げる。
- RQ-YI-005 昇の上限。MMIの範囲の規律に、量・回数の上限と空邑の検出を足す。
- RQ-YI-008 完了間近と完了。EKIの状態区別を、SEIの「汔至」へ広げる。
- RQ-YI-010 正位。TEIの意味の追跡に、位置の正当性を足す。
- RQ-YI-012 革の手続。TEIの移行の要求に、廃止の権限と旧経路の拒否を足す。
- RQ-YI-016 困の検知。EKIのsecurity eventとSEIの未解決に、枯渇の観測点を足す。
- RQ-YI-021 入口の結合。TAIの参照接続を、課題の入口の証拠へ広げる。

## 6. 結合の実在確認

### 6.1 入口の結合は、参照接続として存在する

TAIの`tools/reference-mmi-readonly`は、SCN-001からMMIの読み取り専用MCPを呼び、`inspect`と`select`で表の範囲を取得します。receiptには、MMIのcommit、`package-lock.json`のdigest、Nodeのversion、取得した行のID、原文、出典、版、availabilityを記録します。呼出しの前後で、原本のSHA-256が変わらないことも確認します。

これは、TAIとSHOの入口の結合が、開発用の参照として存在することを示します。2026-11-01に、`tools/reference-mmi-readonly`の`go test ./... -count=1`を実行し、3.5秒で`ok`を確認しました。同じ日に、`tools/reference-scn001`も1.3秒で`ok`でした。参照接続とSCN-001の評価が、この環境で動くことの確認です。実運用の認可、版固定、複数利用者、意味の受理は、引き続き未確認です。

ただし、三つの限界があります。

- 接続は、TAIからMMIへの一方向であり、持ち上げを課題の入口の証拠にする手順にはなっていません。
- `select`のpreviewは最大5行であり、5行を超える表の全行一致は、この経路では確認できません。
- 意味の受理、公開権限、実運用の認可、MMIの書込みは扱いません。

RQ-YI-021は、この接続を入口の証拠へ広げる拡張として残します。

### 6.2 中心の結合は、接続も要求もない

TAIの`tools/reference-sei-decision`は、SCN-001の決定をSEIの一時storeへ記録し、`resume`のprojectionを読みます。原記録の根拠参照を読むモードと、旧い判断が現行対象へ構造上束縛されるかを調べるモードもあります。

2026-11-01に、`go test ./... -count=1`を実行し、22.5秒で`ok`を確認しました。最初の実行では`TestOriginalBasisInspectionThroughSEIVerify`が`invalid character 'g' looking for beginning of value`で失敗しました。原因は、`run`ヘルパーが標準出力と標準エラーをまとめて返し、`go run`のメッセージがJSONの読み取りに混じる可能性があったことです。JSONを読む呼び出しを、標準出力だけを返す`runOutput`へ変えました。変更後に`go test ./... -count=1`を2回実行し、20.8秒と49.9秒で`ok`を確認しています。この失敗は、SEIの意味や構造の失敗ではなく、試験の入出力の扱いの問題でした。

これは、TAIとSEIの接続であり、SHOとSEIの中心の受け渡しではありません。MMIの成果からSEIの判断記録へ到達する経路、SEIの記録からMMIの成果へ戻る経路は、どちらも参照接続として存在しません。要求もありません。

RQ-YI-020は、新規の候補として残します。既存の接続を組み替えるのではなく、二つの既存の記録を、版と範囲を保って往復させる要求です。

### 6.3 参照接続が示すことと、示さないこと

二つの参照接続は、製品間の接続が、開発用の参照として成立することを示します。示さないのは、実運用の認可、複数利用者、版の固定、監査、意味の受理です。本分析は、接続の存在を、結合の価値の証明として扱いません。

参照接続の試験は、2026-11-01に三つを実行しました。SCN-001の参照評価は1.3秒、MMI読み取り専用は3.5秒、SEIの判断記録は22.5秒で、いずれも`ok`でした。SEIの試験は初回に一度失敗し、再実行で通りました。試験の安定性は、別に確かめる必要があります。

## 7. 照合で変わったこと

第一に、候補の数が減りました。最初の22件のうち、要求として残るのは12件です。残る五つは新規、七つは拡張です。残りの十は、既存の要求、受入検査、価値の測り方、レビューの観点へ移します。ハーネスから加わった3件を合わせると、25件のうち15件が要求として残ります。

第二に、優先順位が変わりました。第一巡は、象徴層の境界（017）と主張の規律（018）をP0に置きました。どちらも残しますが、製品の要求ではなく、文書とレビューの規律です。要求としてのP0は、通塞の観測（001）、中心の受け渡し（020）、変爻の検査（019）になります。

第三に、価値の測り方と要求の区別が、はっきりしました。改過（013）、損の設計（015）、汲めること（007）は、要求ではなく、既存の要求と受入シナリオを確かめる測り方です。測り方を要求に混ぜると、実装の対象がぼやけます。

第四に、変爻の検査の一部は、[16-変爻の検査記録](16-変爻の検査記録.md)で実行しました。仮承認のリンク切れと取り違え、廃止済み判断の復活、現行判断と廃止済み判断の対象の取り違えは、参照評価の失敗として観測できました。変種Fでは、対象外のDecisionのリンク切れが検査されずに通ることも確認しました。一般の判断記録の到達性は、まだ検査になっていません。

## 8. まだ照合していないこと

- SEIの受入シナリオ19件のうち、後日の読み直しのシナリオは確認し、RQ-YI-007を既存へ移しました。他のシナリオは未読です。
- EKIの受入シナリオのうち、Contribution RecordにBeneficiaryを残すシナリオと、Browser Workerの停止のシナリオは確認し、RQ-YI-014を既存へ移しました。他のシナリオは未読です。
- TEIのRQ-020の本文。見出しと周辺だけを読み、再実行とtakeoverの範囲が、革の手続と重なるかは未確認です。
- MMIのADR-0028の本文。見出しとContextを読み、出典報告の契約の全体は未確認です。
- EKIのRQ-041の本文。Security eventの一覧を読み、枯渇の観測点は含まれないと読みましたが、本文全体は未確認です。
- 各製品のADRが、候補と同じ内容を設計判断として持っている可能性。

これらを読むと、分類が変わることがあります。とくに、受入シナリオに後任の到達が入っていれば、RQ-YI-007は受入検査から既存へ移ります。

[15-生成AIハーネスの卦読み](15-生成AIハーネスの卦読み.md)から、三つの候補が加わりました。既存の要求との照合は、予備的なものです。

## 10. 結論

第一巡の候補は、読みから出た提案として有用でしたが、既存の要求との重複が多すぎました。本資料は、25件の候補のうち15件を要求として残し、十を既存の要求、受入検査、測り方へ戻します。

この修正は、分析の失敗ではありません。卦の読みから候補を出し、既存の要求へ照らして落とす。この往復が、読みを要件へ移す手続きです。残った15件も、まだ候補です。各製品のOwnerの採否を経て、初めて要求になります。
