# 意味変更の進め方（2026-11-06）

TEIの契約を変えるとき、TAIがどの順で何を直すかを、3回の実測から固定した手順書です。計画§7.7の段階5・6で使った手順をそのまま書いています。

対象はパイロット（`integrations/pilot-sui-document`）の5契約です。製品の実装は変えません。

## 1. 順序

**被覆 → 再生成 → 適合 → 写像**の順で進めます。この順序を守る理由は、逆にすると「試験が緑のまま変更が壊れている」状態を通してしまうからです。

| 手順 | 何をするか | 落ちたら |
| --- | --- | --- |
| 1. 意味を決める | 契約（`candidates/*/contract.json`）を変える。版を上げる | ― |
| 2. 被覆を確かめる | `fixture_field_coverage_check.py`。新しい意味を exercise するケースが無ければ落ちる | 3へ進む前に、落ちることを確認する |
| 3. 被覆を足す | `fixtures.json` にケースを足す／既存ケースの期待値を直す | ― |
| 4. 再生成する | `tei-generator-build` で候補を作り直す | 契約の書き方の問題。生成コードは手で直さない |
| 5. 適合を通す | `integration_flow.py` で全ケースが通ることを確認する | 契約かfixtureのどちらかが違う |
| 6. 写像を追随させる | 製品の消費側（`from_artifact`など）が新しい意味を知っているか確認する | 食い違いは製品変更として記録し、TAIでは直さない |

2で「落ちない」場合は、**その意味変更は試験に届いていない**と判断します。被覆を足してから5へ進みます。

## 2. 実測した費用

3回の意味変更で、どこをどれだけ直したかです。生成コードの手修正は**3回とも0行**でした。

| 変更 | 契約 | 被覆 | 検出 | 写像 |
| --- | --- | --- | --- | --- |
| 任意フィールドの追加（Island `summary`） | 1ファイル | 新規1ケース | **検出しない**（被覆を足すまで緑） | 追随が必要（新しい意味は落ちる） |
| 必須フィールドの追加（Card `revision`） | 1ファイル | 既存3ケース＋新規1件 | **検出する**（全presentケースがmissingになる） | 追随が必要 |
| 任意→必須（Island `title`） | 1ファイル | 既存1ケースの書換 | **検出する**（欠落ケースが落ちる） | **不要**（フィールド集合が変わらない） |

- 人の手が入るのは**契約1ファイルとfixtures1ファイル**だけ
- 検出できるかどうかは「その項目を欠いた状態を exercise するケースが既にあるか」で決まる
- 写像の追随が要るかどうかは「フィールドの追加・削除があるか」で決まる

## 3. 変えてはいけないもの

- **生成されたコードを手で直さない。** 直すべきは契約かfixture。生成コードを直すと、次の再生成で消える
- **写像をTAI側で自動化しない。** 製品の意味への写像は製品の責務で、TAIが下流に回避実装を足すと、TEIの不足が見えなくなる
- **receiptの`scope`を生成側で書く。** 生成されるreceiptファイルを直接書き換えても、次の実行で上書きされて戻る（実際に踏んだ）

## 4. 記録すること

1件の意味変更につき、次の4点をreceiptに残します。receiptの書式は既存の3件（`TEI-meaning-change-*.json`）に合わせます。

- 何を変えたか（契約・版・追加/変更/削除した項目数）
- 被覆を足す**前**に、被覆検査と適合試験がどうだったか
- 被覆を足した**後**に、両方が通ったか
- 写像の追随が要るか、要るなら何を直すか（TAIでは直さず、製品側の判断として記録）
