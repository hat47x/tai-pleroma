# TEIによるプロダクト構築への移行 — フィージビリティ検証計画

状態: **Draft（提案）**。Owner指示（2026-11-01）を前提にした検証計画であり、製品要求・採用済み設計ではありません。

現況（何が示せて何が示せていないか・判断が要る点）は[TEIパイロットの現況](tei-pilot-status-brief.md)に1枚でまとめています。要求の正本は各リポジトリの`requirements/`、TEIの方法は[TEIの業務システム設計要求](https://github.com/hat47x/tei-platform/blob/main/requirements/BUSINESS_SYSTEM_DESIGN_REQUIREMENTS.md)を参照します。

## 1. 前提とする方向

TAI配下の自作プロダクト（TAI、EKI、SUI、SEI、MMI、TEI自身を含む）は、TEIによる構築へ移行する前提にあります。この移行の実装に耐えることを、TEIのフィージビリティ検証と、各プロダクトの生成AIを用いた開発効率・自律性の向上検証として扱います。

したがって、個別プロダクトの機能追加は、移行後にTEIの意味モデルと生成器で表現できるかを意識して行います。ただし、移行の実現性が確認できるまでは、既存プロダクトの実装を止めません。

## 2. 「TEIで構築する」の操作的定義

抽象的な「TEIで作る」を、検証できる条件に分解します。

| 条件 | 意味 | 確認方法 |
| --- | --- | --- |
| 意味が正本 | データ・機能・業務の意味が、生成物のコードとは別に版付きで存在する | 意味の変更がdiffで追え、生成物と対応づく |
| 生成単位が生成器 | 案件ごとのコードではなく、意味から生成器を導出・選択できる | 同じ意味から複数の成果物を再生成できる |
| 適合試験がある | 生成物の正しさを、意味とは独立した試験で確認できる | 生成物の差し替え後も同じ試験が通る |
| 実行先が交換できる | Target Profileを変えても意味と試験を引き継げる | 別の実行先で同じ適合試験が通る |
| 証拠が版に束縛される | 生成器・成果物・試験のdigestが記録される | receiptから版と結果を再確認できる |

このうち一つでも欠ける場合、「TEIで構築した」とは呼びません。現在のTEIは、生成器の選抜・来歴・artifactとTarget Profileの参照実装を持つ一方、統合モデラーと編集環境は未完成です（[TEI status](https://github.com/hat47x/tei-platform/blob/main/docs/status.md)）。この差を、パイロットでどこまで埋められるかを確認します。

## 3. パイロットの選定

第一候補は**SUIの再構築**です。理由は次のとおりです。

- マルチテナント化より先に、TEIによる再構築を進める方針が決まっている（Owner指示 2026-11-01）。
- SUIはデータ・機能・業務の三視点が比較的明確で、DocumentV1、card、island、edgeという意味の単位を持つ。
- 現行SUIには参照実装と試験があり、生成物と比較する基準を作りやすい。

ただし、SUI全体を一度に移行しません。最初のパイロットは**DocumentV1の読み取りとcard/island/edge投影**に限定します。意味形成のUI、認可、テナント分離は対象外とし、別の判断に分けます。

## 4. 三視点のモデル化範囲（パイロット）

| 視点 | パイロットで扱う範囲 | 正本・参照 |
| --- | --- | --- |
| **データ** | DocumentV1、Card、Island、Edge、digest | SUIの型定義と合成document |
| **機能** | documentのPUT/GET、card/island/edgeへの投影、digest照合 | SUI APIの参照実装 |
| **業務** | 誰が意味を受理するか、誰が文書を読むか、何を未決のまま残すか | SCN-001の観測・仮説・判断の分離 |

業務の視点は、パイロットでも省略しません。意味の受理者を決めずに生成器だけを作ると、生成物の正しさを誰が判断するかが空になります。

## 5. フィージビリティ判定

パイロットの合否は、次の5条件で判定します。

1. 意味の変更から成果物を再生成でき、手作業の修正が不要または限定されている。
2. 生成物が既存の適合試験（または移行後に定義する試験）を通る。
3. Target Profileを一つ選び、その実行先で動作する。
4. 生成器・成果物・試験のdigestがreceiptに残り、後から再確認できる。
5. 上記を、人が同じ手順で再現できる。

「生成できた」ことは、業務上の正しさや利用者価値の証拠にしません。

現時点の判定は[TEIパイロットの判定](../analysis/tei-pilot-conclusion-2026-11-06.md)にまとめています。**結論は未達**で、条件ごとに「示せた／部分／反例」と、何が変われば達するかを書いています。判断が下りたときに何を測り直すかは[再観測の準備](re-observation-plan.md)に、実行コマンドと期待値つきで書いています。

## 6. 効率・自律性の測定

移行の効果は、次の指標で測ります。比較の基準は、現行SUIの該当範囲を手作業で変更した場合とします。

| 指標 | 何を見るか | 注意 |
| --- | --- | --- |
| 変更から再生成までの時間 | 意味の変更を決めてから、試験が通る成果物が出るまで | 待ち時間と人の作業時間を分ける |
| 手修正の量 | 生成物へ人が加えた変更の行数・箇所数 | 意味の修正と生成器の修正を分ける |
| 人の介入回数 | 指示・確認・やり直しの回数 | 介入の種類を記録する |
| 試行回数 | 生成AIが失敗して再試行した回数 | 失敗の原因分類を持つ |
| 文脈量 | 生成AIへ渡した意味・コードの量 | 削減が目的化しないよう、精度と併記する |
| レビュー指摘 | 生成物に対する指摘の件数と種類 | 意味・実装・運用に分ける |

これらの指標は、一つのパイロットの観測であり、一般的な生産性の証明ではありません。比較条件（同じ変更、同じ評価集合、同じ環境）をreceiptに残します。

### 判定（2026-11-02時点）

示せたこと:

- 文字列投影の1属性で、意味→契約→生成→選抜→one-shot Target Profile実行まで通った。
- 2属性目（document_id）も同じ生成器で生成・選抜・実行できた。
- 生成と選抜のツール工程の時間・試行回数・介入回数をreceiptへ記録できた。

示せていないこと:

- Island/Edgeの投影と、SUIの実装コードの生成。
- 実機・実OS・実配備、人の受理、意味の正しさ。
- 生成AIの生産性・自律性の向上（PoC中は評価せず、完成後に評価する）。

判断の選択肢:

1. パイロットをIsland/Edgeへ広げる。
2. 実環境に近いTarget Profileへ進む。
3. TEI側の統合モデラー整備を待つ。

### 評価の位置づけ（2026-11-02、仮決定）

本開発はPoCであり、生産性の評価はプロダクト完成後に行います。PoC中に中間評価を人への判断材料として出しません。細部の判断は完成後でないと困難なため、ここでは仮決定として置き、必要になった時点で見直します。

`measure_workflow.py`とT1比較のreceiptは、生成AIが自分の進め方を振り返り、次の作業を選ぶための材料です。人による受入判定、生産性の評価、自律性の証明には使いません。

したがって「生産性が未確認」は未達項目ではなく、現段階では評価しない項目として扱います。

### 7.7.1 意味変更2件の実測（2026-11-06）

| --- | --- | --- |
| 意味の変更 | Island に任意の `summary` | Card に必須の `revision`（`std.integer`） |

| 適合試験（被覆追加の前） | 24/24 PASS | 失敗（全presentケースがmissingになる） |
| 被覆の手修正 | 新規1ケース、既存0件 | 既存3ケース＋新規1ケース |

| Profile | 実行モデル | 結果 |
| --- | --- | --- |
| `sui-record-oneshot` | oneshot | PASS（5プロセス・5リクエスト・5応答） |
| `sui-record-rolling` | long-running | **FAIL**（1プロセス・5リクエスト・1応答、`candidate wait failed: exit status 2`） |
| `sui-text-oneshot` | oneshot | PASS（4プロセス・4リクエスト・4応答） |

理由は生成候補の側にある。生成テンプレート（`text-template`と`text-record-template`）が出力するプログラムは、標準入力から1件読んで1件返して終わる。long-runningプロファイルは1プロセスに複数リクエストを送るため、2件目で候補が既に終了している。**2つのテンプレートで同じ非対称が出たので、特定テンプレートの欠陥ではなく生成物の共通の性質**である（[text側の比較](../evaluations/records/TEI-target-profile-compare-text-2026-11-06.json)）。

- これは"実行先が交換できる"の反例であり、生成テンプレートがprocess modelごとに要ることを示す。TEI側の論点として追加する（入れ子・数値配列に次ぐ3件目）

### 7.7.1-d 十進値の精度（2026-11-06）

TEIの`plan/workstreams/TEI_PRODUCT_CRITICAL_PATH_2026-10.md`§34は「投影のJSON化で十進値の`float64`経由の精度喪失、optionalのmissing/null同一省略などがあり得る。実消費値の忠実度は#2585の別検査であり、生成成功≠型付き意味保持」と書いている。**TAIのパイロットでも同じかを測った。**（[receipt](../evaluations/records/TEI-decimal-fidelity-2026-11-06.json)）

Card契約の`x`（`std.decimal`）に桁数を与えて、投影された値を`Decimal`で比較した。

| 入力 | 投影後 | 一致 |
| --- | --- | --- |
| `10` | `10` | 一致 |
| `0.1234567890123456789` | `0.12345678901234568` | **不一致**（下位桁が丸め） |
| `0.0000000001` | `1E-10` | 一致 |
| `12345678901234567890` | `12345678901234567000` | **不一致**（2^53超の整数が丸め） |
| `0.1` | `0.1` | 一致 |

- TEIの記載どおり、**十進値は`float64`を経て丸められる**。整数でも2^53を超えると失われる
- パイロットの用途では座標が`float64`なので実害は小さいが、「生成成功≠型付き意味保持」は**TAIの契約でも成り立つ**
- `optional`のmissing/null同一省略も、TEIの記載と一致する（Edge契約v4で実測済み）
- これらは#2585としてTEI側で既に追跡されている。TAIは新しい論点を作らず、**同じ現象が自分の契約でも起きることの証拠**として記録する
- 値の丸めを避けたい契約（金額など）では、`std.decimal`のままだと足りない。TEI側の判断（#2585）を待つ

  - Target Profile比較の`comparisonPassed`: long-runningで通らないことを示す（text側も同じ）

### 7.7.1-f 実行モデルの反例の原因を特定（2026-11-06）

long-runningプロファイルで通らない原因を「生成候補が1件で終わるから」で止めていたが、TEIの生成器の構成を確かめて、より正確にした。[receipt](../evaluations/records/TEI-projection-strategy-2026-11-06.json)

- TEIにはlong-running用のテンプレートがある（`template-long-running.go.tmpl`、Python/Java/JS/WASM/WASIの同種もある）
- しかし**投影（`projection: true`）の戦略は`text-template`と`text-record-template`の2つだけ**で、どちらもone-shotのmainを出す
- 投影契約にlong-running用の戦略を渡すと、生成器が拒否する

```text
tei-generator-build -strategy long-running-template（projection kind "record"）
→ projection kind "record" requires the text-record-template strategy
tei-generator-build -strategy long-running-template（projection kind "normalize"）
→ 同じく拒否
tei-generator-build -strategy text-record-template → 生成できる（one-shot）
```

つまり **「long-runningが無い」のではなく、「long-runningで動く投影の生成戦略が無い」**。TEI側の論点は「生成テンプレートをprocess modelに対応させる」ではなく、**「投影戦略をprocess modelに対応させる（または投影契約にlong-runningテンプレートを許可する）」**と書くほうが正確である。Issue草案3件目をこの表現に直した。

さらに、この組み合わせは**TEIの試験にも文書にも無い**ことを確認した（`*_test.go` 1629件と`docs/`・`plan/`の全文検索で0件）。コードの中の暗黙の結合であり、意図した制約として宣言されているわけではない。したがって論点は「設計どおりか」ではなく**「組み合わせが検証されていない」**になる。

### 7.7.1-g TEI側3件の性格の違い（2026-11-06）

3件を同じ「不足」として並べていたが、TEIの試験を当たると性格が違った。

| 件 | TEIの試験 | 性格 | 依頼の種類 |
| --- | --- | --- | --- |
| デコード方針（入れ子・未知フィールド） | 無い | 暗黙の挙動 | 方針の決定 |
| 数値・真偽値の配列（`many`） | **有る**（`projection_pfc_many_test.go`が拒否を表明） | **意図した制約** | 拡張の提案 |
| 投影×process model | 無い（1629件で0件） | 暗黙の結合 | 未検証の指摘＋方針の決定 |

- `many`の制約には「実行時は文字列しか扱えない」という理由が試験のコメントに書かれている。**不具合ではなく仕様**なので、「壊れている」と報告しない
- 残る2件は、コードにだけ挙動があり、試験でも文書でも宣言されていない。**決まっていないことを決めてもらう**依頼になる
- 3件を同じ調子で並べると、`many`が不具合に見えてしまう。依頼の種類を分けて書く

この区別は、TAIが「製品の設計判断が要る」と言う前に**製品の試験を読む**という順序から来ている。前段の製品文書の確認と同じ種類の手順で、次回以降も先に試験を当たる。

### 7.7.2 段階5の結論（2026-11-06）

段階5の出口を、達成・反例・保留に分けて締める。

| 出口 | 状態 | 根拠 |
| --- | --- | --- |
| 1. 意味変更2件以上の1回転 | **達成** | 任意フィールド追加と必須フィールド追加の2件（[optional](../evaluations/records/TEI-meaning-change-2026-11-06.json)、[required](../evaluations/records/TEI-meaning-change-required-2026-11-06.json)） |
| 2. 写像の追随を手修正として計上 | **達成** | どちらも契約1ファイル＋fixtures1ファイル。生成コードの手修正は0行 |
| 3. 別Target Profileで同じ適合試験 | **反例** | one-shotは通り、long-runningは通らない。原因は生成候補の実行モデル（[record](../evaluations/records/TEI-target-profile-compare-2026-11-06.json)、[text](../evaluations/records/TEI-target-profile-compare-text-2026-11-06.json)） |
| 4. 判定表の更新 | **達成** | §7.8を実測に合わせて更新 |

段階5で確定したこと:

1. **意味変更の費用は、意味の形で変わる。** 任意の追加は「試験に届かない」（被覆を足すまで緑）、必須の追加は「試験が壊れる」（既存ケースが一斉に落ちる）。どちらも生成コードは自動で追従し、人が直すのは契約とfixturesだけ。
2. **適合試験は意味の変更を検出しない。** 検出するのは被覆の有無であり、被覆は意味変更のたびに人が足す。段階5ではこれを検査（被覆0件のフィールドを名指しで落とす）で強制した。
3. **製品の写像は生成されない。** 消費側は既知フィールドに忠実だが、新しい意味は`valid: true`のまま落ちる。写像の追随は意味変更1件あたり1ファイルの手修正として計上する。
4. **実行先の交換は、生成候補の実行モデルを変えない。** Profileの宣言を差し替えても、process modelが変われば候補は動かない。

### 7.7.3 次の段階（仮決定・2026-11-06）

段階6は、TAIが単独で進められる範囲では**新しい検証を増やさず、再生成ループの運用を定着させる**段階にする。理由は、意味変更の費用・被覆の強制・写像の追随・実行モデルの4点が揃い、これ以上パイロットの範囲を広げても同じ結論の反復になるためである。

| 項目 | 内容 |
| --- | --- |
| 目的 | 決めた運用（被覆を先に落とす、写像の手修正を計上する）が、次の変更でも回ることを確かめる |
| 出口 | 3件目の意味変更を、被覆検査→被覆追加→適合→写像追随の順で記録する。写像の追随が不要だった場合はその理由を書く |
| 停止条件 | TEI側3論点（デコード方針、数値配列、process model）のいずれかに判断が出たら、範囲を広げる前に再観測する |
| 非目標 | パイロット範囲の拡大（SUI全体、書き込み経路、複数プロダクト接続） |

範囲を広げない理由は、段階4で「TEI側の不足を先に埋める」と決めたことと同じである。TAIの側で範囲を広げると、未解決の不足を下流の回避実装で覆い隠すことになる。

### 7.7.4 段階5・6の運用の定着（2026-11-06）

段階5・6で回した「意味変更→再生成→被覆→適合→写像」の手順を、[意味変更の進め方](meaning-change-runbook.md)として固定した。3回の実測から、次の3点を運用規則にしている。

1. **順序は被覆→再生成→適合→写像。** 逆にすると、被覆の無い変更が緑のまま通る
2. **被覆検査が落ちない変更は、試験に届いていない。** 被覆を足してから適合へ進む
3. **写像はTAIで自動化しない。** 製品の意味への写像は製品の責務で、下流に回避実装を足すとTEIの不足が見えなくなる

段階6の当初の狙い「新しい検証を増やさず運用を定着させる」に対して、実際には検証を4つ足した（体裁、登録漏れ、`result`と終了コードの一致、`PASS`と成功フラグの矛盾）。いずれも**「緑なのに嘘」を1件以上実際に捕まえた**か、捕まえる形を自己試験で示したもので、運用の定着を支える検査として残す。この判断も残しておく（増やすこと自体を目的にしない）。

## 7.9 receiptの体裁の棚卸し（2026-11-06）

「証拠が版に束縛される」を示せた一方で、receiptの体裁は機械的に検査していなかった。`scope`（何を証明しないか）を毎回書く運用は、検査が無ければ抜ける。

- 一括検証のcheckerは**登録済みの247件**（実実行185・合成61）だけを見るため、未登録のreceiptは検査をすり抜ける。この棚卸しは全258件を対象にした
### 修復の結果（同日）

見積もった2種類の修復を実施した。

体裁を直したあと、**checkerに登録されていないreceipt**が残っていることが分かった。checkerは登録済みのものにしか意味の規則を当てないため、未登録は「体裁は正しいが中身は検査されない」状態になる。

## 8. 停止条件・非目標

- フィージビリティが確認できるまで、既存プロダクトの本番移行や公開は行いません。

- 公開gateは`blocked`のままです。
